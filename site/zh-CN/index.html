您的智能体无法相互交流。给它们一座大使馆。

Embassy 是一个本地单用户网关：您运行中的 Claude Code 会话和 Codex 桌面任务在同一台机器上双向交换消息，每一步都经过操作者的明确操作。每次被接受的发送都会返回一个投递令牌，并最终进入一个明确的终态。

为什么

当两个工具需要交谈时。

您的 Claude 会话在工作流中途向您的 Codex 任务提问——您无需切换窗口或粘贴任何内容。

Codex 在您离开时向 Claude 发送问题；回复被路由回来，回执确认已投递。

Claude 使用其原生工具向运行中的 Codex 任务发送消息——无需安装插件，无需编写配置。

工作原理

五个步骤，仅限必要的那些。

无需 Embassy 账户、无守护进程、无配置文件——五个动作，每一个都在您的终端中可见。

1启动在您信任的终端中运行 embassy serve。它保持在前台运行，将静态仪表盘页面——gateway-dashboard.html 及其 gateway-dashboard.zh-CN.html 版本——写入其私有状态目录，且永不守护进程化。主机级租约确保每个账户只有一个代理。
2注册Codex 任务从其自身进程内部注册——要求 Codex 智能体在当前回合中将 embassy register-codex --alias codex-reviewer@this-mac 作为 shell 步骤运行。注册是选择加入的边界：一旦注册，以您的操作系统用户身份运行的任何兼容活跃 Claude 会话都可以在该任务中启动一个回合，遵循其现有的原生审批和沙盒策略——如果该策略是 approvalPolicy: never，则已接受的消息和模型回合之间没有人工审批。到达 Codex 任务永远不会为反向方向选择该 Claude 会话。使用 unregister-codex 注销。
3选择对于 Codex→Claude 方向，您需要显式选择目标——embassy select-claude --alias <a name from availablePeers>。发送永远不会静默选择已发现的会话。
4发送消息正文通过 stdin 传入，最大 16 KiB，仅存在于内存中。向繁忙的 Codex 任务发送消息会排队；空闲的目标会获得一个普通回合。
5监控可选。embassy dashboard --live 打开同一元数据的只读浏览器视图——一个在 127.0.0.1 上的独立前台进程，经过认证且无法发送任何内容。状态目录中的 gateway-dashboard.html 是惰性离线副本：无脚本、无网络、无自动刷新——重新运行 embassy refresh-dashboard 并刷新页面。
协议真相

记录不会粉饰。

Embassy 的回执严格表达其字面含义——不多也不少。

已投递意味着接收方已接受消息，而非模型已完成处理。对于 Codex 方向，这指 App Server 接受了该回合；对于 Claude 方向，这指消息已释放到会话的原生队列中——并非已读取，也并非已完成。没有原生终端回执的已确认写入报告为 unconfirmed；不确定的写入报告为 ambiguous，且永不自动重试。CLI 的初始接受会返回一个会话令牌和一个投递令牌；held 和 transport_written 是过程状态，而非成功状态。源自 Claude 的失败以原生 expired 状态结算，随后附带一个包含安全代码的静态诊断帧——永不包含路径、标识符或原始异常。

队列是诚实的。向繁忙的 Codex 任务发送消息会排队而非中断——Embassy 从不干预另一个智能体的回合内上下文。排队的消息在目标空闲后按顺序排出，队列存留时间在仪表盘上可见——永不静默。

重启会丢弃消息正文，这是有意为之。消息文本永不持久化——不在状态中、不在日志中、不在事件中、也不在仪表盘中。如果代理停止，排队的文本即刻消失，不会重播任何内容。

未知版本以关闭方式失败。Claude Code 2.1.226，对等协议 1——仍在运行的 2.1.224 与 2.1.225 会话通过补丁升级保持兼容——以及 Codex App Server 0.147.0。Embassy 无法验证的任何内容都会被拒绝，而非被猜测为兼容：无法识别的会话不可发现，无法识别的 App Server 结构会使路由不可写入。新版本的支持随发布版本一同提供——参阅更新日志。

embassy serve 不打开任何 TCP 或 HTTP 监听器；可选的实时伴侣组件才会。embassy dashboard --live 是一个独立的前台进程，在临时端口上绑定 127.0.0.1，用于只读认证元数据流——无修改操作、无提供商接口、无 CORS 表面。认证作用域是浏览器，而非机器：以您的操作系统用户身份运行的任何进程——包括 root 和浏览器扩展——都能读取浏览器能读取的内容。embassy serve 本身不打开网络监听器，也不发起任何提供商 API 调用——无遥测、无云端组件。它仅通过本地 Unix 套接字通信：其 mode-0700 状态目录中的控制套接字，以及它连接的提供商拥有的 Claude 对等套接字和已在运行的 Codex App Server 套接字。智能体本身仍由云端支持：路由的消息成为普通模型回合的输入，因此其文本会到达 Anthropic 或 OpenAI，就如同您亲自在该会话中键入一样。"本地"描述的是代理和路由，而非模型推理。

这是一条新的输入路径。没有任何智能体获得它原本没有的工具，Embassy 不授予、不放宽、也不回答任何东西。但两个原本无法交换文本的产品现在可以了——请将每条路由消息视为可能引导其接收方的不可信输入。

快速开始

先说真实的前提条件。

  • 仅限 macOS（仅限 localhost）· Node.js ≥ 20
  • Claude Code 2.1.226，已安装并登录——需有会话运行中，否则 availablePeers 为空
  • Codex 桌面版及其托管的 App Server 0.147.0 运行中
# 安装并启动代理（前台运行，在受信任的终端中）
npm install -g agent-embassy
embassy serve

# 在另一个终端中：列出 Embassy 发现的候选会话
embassy status
  availablePeers: ["advisor@this-mac", "researcher@this-mac"]

# 可选，在第三个终端中：在 127.0.0.1 上的只读浏览器视图
embassy dashboard --live

# 在 Codex 任务内部——要求 Codex 智能体将此作为 shell 步骤运行：
embassy register-codex --alias codex-reviewer@this-mac

# 作为操作者：从上面的 availablePeers 中选择一个名称（您看到的会有所不同）
embassy select-claude --alias advisor@this-mac

# 从 Codex 任务发送（正文通过 stdin 传入，不通过参数）
embassy send-to-claude --from codex-reviewer@this-mac --to advisor@this-mac --expects-reply <<'MSG'
Please review the current approach and note the main risk.
MSG

# 使用返回的令牌继续对话，双方均可发起
embassy reply --conversation conv_<token> --alias codex-reviewer@this-mac <<'MSG'
Please expand on the second call site.
MSG

# 另一个方向无需任何操作：运行中的 Claude 会话
# 在其原生 ListAgents 中看到 codex-reviewer 并直接发送消息。

完整的快速开始指南——会话 UUID 寻址、投递语义、仪表盘——请参阅 README。
