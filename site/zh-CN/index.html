为什么

它为这三个时刻而存在

如果你同时运行不止一个智能体，你早已熟悉它们。

工作中途

你的智能体有一个问题

Claude 碰到一个 Codex 已经做过的决定。不必你在两个窗口之间来回搬运上下文，它自己去问 — 并在等待回复期间继续工作。

人不在桌前

回复无需你在场即可送达

朝向 Codex 的问题会诚实等待任务空闲后的回合边界；返回 Claude 的答案则会立即进入其邮箱，即使 Claude 正繁忙。无需你盯着终端。

足迹极小

几乎不需要安装任何东西

Claude 完全不需要 Embassy 命令 — 其原生 ListAgents 与 SendMessage 即可发现并联系 Embassy 向它公布的对端。Codex 任务只需运行一条 CLI 命令完成注册。DeepSeek 与 Grok Build 在配置中声明，由 broker 在有消息需要它们时才启动。

提供方

四面旗帜，一道大门

Claude Code 与 Codex 保留各自的原生传输，因为只有它们能把消息送进你已经打开的实时会话。DeepSeek 与 Grok Build 经由 ACP（开放的 Agent Client Protocol 标准）接入，作为 Embassy 启动并持有的会话。四者都走同一个 broker、同一套同意边、同一本台账。

Claude Code

经由私有 Unix domain socket 的原生对端协议。邮件落入你正在使用的实时会话：发现、选择，以及一次带有相关联原生回执的邮箱写入。peerProtocol 1 是严格的线上语法，逐条记录校验。

Codex

经由 Embassy 自有本地子进程的托管 App Server。已注册任务会被恢复并观察；消息在空闲回合或经校验的工具调用边界进入 — 绝不在生成中途插入。

DeepSeek

由 Embassy 从你本地的 dsh harness 检出目录（DSH_HOME，默认 ~/.dsh）启动的 ACP 会话 — 已发布的 adapter 无法直接 spawn。没有检出目录就不假装有：该路由会带着确切的 safe code 显示为降级。它的回执是有意粗粒度的；见协议一节。

Grok Build

来自注册表精确固定制品的 ACP 会话 — npx --yes @xai-official/grok@1.0.5 agent stdio。无需打包任何 adapter。能力取自本连接 initialize 响应中所读到的内容，读到什么就按什么处理，绝不预先假定。

下一面旗帜的成本：ACP 客户端 562 行，共享的 provider 适配层 212 行。DeepSeek 与 Grok Build 合计以不到 800 行改动落地 — 各自只是一份启动规格加一份诚实的回执映射，而不是一套新传输。随之而来的诚实限制：ACP v1 只能 spawn，因此 ACP 提供方是通过 Embassy 自有的会话与你对话，而不是你在另一个窗口里打开的 TUI。

工作原理

六条命令建立一条可用路由

每条命令与已发布的 CLI 逐字一致。

embassy serve

启动 broker。它不开启任何网络监听 — 一切留在这台机器上。配置中声明的 ACP 提供方会在启动时注册各自的路由（默认 dsh-main@this-mac 与 grok-main@this-mac）；它们的子进程按需惰性启动，直到第一条需要它的消息到来。

embassy register-codex --alias codex-embassy@this-mac

在 Codex 任务内部运行 — 身份从任务继承，绝不冒充。请让你的智能体来执行。

embassy select-claude --alias claude-main@this-mac

选择 Claude 路由。选择不会创建同意边。

embassy pair --from codex-embassy@this-mac --to claude-main@this-mac

显式创建下一条发送将使用的双向同意边。两端必须都已注册、在线、位于同一主机，且分属不同提供方。

embassy send --from codex-embassy@this-mac --to claude-main@this-mac <<'MSG'

信封过境 — 正文经 stdin 传入，绝不作为参数。你会收到一个 dlv_ 回执和一个 conv_ 令牌。

embassy dashboard --live

看着回执结算，措辞诚实 — 或用 embassy status 获取一次性快照。

协议真相

这本台账不会奉承你

下面每一条声明的含义与字面完全一致 — 这正是产品本身。

delivered ≠ 已读

朝向 Codex 时，delivered 表示 App Server 已接受轮次；朝向 Claude 时，表示原生邮箱写入完成；朝向 ACP 提供方时，表示该提供方的会话对这次 prompt 作出了应答。三者都不暗示正文被阅读、理解或执行。

方向决定投递时机

朝向 Codex 的消息等待空闲，或使用精确 STEER 的下一个工具调用边界；朝向 Codex 的等待可能显示为 held — 是进展而非成功 — 且 Embassy 绝不中途打断生成。朝向 Claude 的消息无论繁忙还是空闲都会立即进入其邮箱。朝向 ACP 的消息在派发时即发出 prompt，智能体的回答沿同一会话返回。

说清测过什么，而不是认证

一个发布版说明它测试过什么 — 提供方、传输、确切制品、协议，以及每条通道诚实的限制 — 全部写在一份归发布所有的支持矩阵里。它是关于我们测试范围的声明，不是运行时的许可系统：有测试证明运行中的 broker 从不引用这份矩阵文件。

运行时只声称它证明过的事

运行时不存在证据等级、兼容性探测，也没有任何版本闸门。路由权限来自同意加上确切的自有路由身份；成功只等于本次连接、本条路由与本次相关联操作所展示出的结果。版本号是未经验证的元数据，任何版本事实都不授予也不收回任何权限。

unconfirmed 才是诚实的回执

DeepSeek 的 adapter 把 aborted、blocked 与 error 结果统统压成 end_turn，因此这条通道上的 end_turn 什么也证明不了。Embassy 将其结算为 unconfirmed 并附 ACP_OUTCOME_COARSE，而不是称之为 delivered。真正的取消仍结算为 cancelled。这一压缩发生在上游，客户端侧无法还原；在上游适配器如实报告之前，回执将保持诚实。

重启不再丢邮件

排队中的邮件在 broker 重启后幸存，并在路由恢复时恰好重发一次。崩溃时在途的消息结算为 ambiguous — 绝不悄然丢失，也绝不重复发送。

同意按边授予，每条消息都标明来源

被路由的消息需要两端之间存在一条确切的同意边 — 与两端 lease 绑定、不分角色的记录 — 且默认就是 paired inbound；embassy serve --inbound open 是唯一一种刻意放宽它的方式。每条被路由的正文都装在一个由 broker 组装的来源信封里，注明发送方、来源提供方与回复令牌：这份归属发送方无法伪造。

操作系统边界就是防线

embassy serve 不绑定任何端口。身份在操作系统边界上被认证 — 同一台机器、同一用户、确切的可执行文件、私有的 0600 socket 与状态文件 — 而不是靠一个名字自称。可选组件是唯一的 loopback 监听者：精确 127.0.0.1，默认稳定端口 41961 或单次命令的 --port，并在可信单用户机器上有意不设身份认证。

一切都有界

被接受的消息上限 16 KiB；ACP 回复上限 64 KiB，超出部分标记为截断而非悄悄裁掉；队列、会话、保留与期限全都有界；智能体子进程死亡后按固定退避阶梯重试，而不是空转。对每一个 ACP 权限请求，Embassy 一律回以拒绝 — 从不批准。

路由消息是一条新的输入路径

把任何到达的内容当作接收方的不可信输入 — 与对待任何工具结果相同的纪律。

delivered

该方向的提供方边界已跨越：App Server 接受了朝向 Codex 的轮次，Claude 原生邮箱接受了朝向 Claude 的写入，或某个 ACP 会话对 prompt 作出了应答。三者都不表示已读。

unconfirmed

Embassy 无法确认该方向的投递边界 — 包括提供方自己的 adapter 毁掉了证据的情形。不是失败；也不是成功。它保持 unconfirmed，而不是去猜。

ambiguous

关于结算的信号相互矛盾，或子进程在结果未定时死亡。与 failed 不同 — broker 报告它所知道的，而不是看起来整洁的。

expired

消息期限在结算前已过。终态，并在台账中连同导致它的期限一起可见。

仪表盘

看着大使馆运转

可选的实时仪表盘：broker 健康状态、交换面板、可按来源与目标提供方筛选的每条投递生命周期、同意拓扑与诚实的诊断 — 包括有界保留、只属于本机的消息正文。静态快照 — gateway-dashboard.html 及其 gateway-dashboard.zh-CN.html 孪生页 — 保持仅元数据，完全不需要服务器。

词汇表

每个词都言之有物

注册与同意边

权限模型。Codex 任务自行注册；Claude 会话与之配对；ACP 路由在配置中声明并于启动时注册。一条边就是允许其中两者通话的那个有意动作，且只有配对双方可以通话 — 除非你刻意开放 inbound。

台账

每次投递的回执，状态措辞绝不夸大。当你问"我的消息在哪里"时，它是权威记录。

邮袋

转运。途中密封：broker 只搬运消息，不阅读消息。

快速开始

五分钟内跑起来

先说要求：macOS · Node ≥ 20 · 当前 agent-embassy 版本 · 声明 peerProtocol 1 的 Claude Code · 托管 Codex App Server；它们都在同一台机器、同一 OS 用户下。ACP 提供方是可选的，各自另有前提：DeepSeek 需要一份本地 dsh harness 检出目录和它自己的凭据，Grok Build 需要其注册表固定的包可被 npx 解析。不存在的提供方会带着 safe code 显示为降级 — 不会因为版本缺失或出乎意料就拒绝启动。仅单用户、仅同机。Claude 侧不需要任何 Embassy 命令（原生 ListAgents/SendMessage）；只有 conv_ 令牌持有者可以 reply。

$ npm install -g agent-embassy
$ embassy serve
# 在你的 Codex 任务内部 — 请让智能体来运行：
$ embassy register-codex --alias codex-embassy@this-mac
# 操作者：从 `embassy status` 的 availablePeers 中选一个名字：
$ embassy select-claude --alias claude-main@this-mac
# 创建下一条发送将使用的同意边：
$ embassy pair --from codex-embassy@this-mac --to claude-main@this-mac
# 在 Codex 任务内 — 正文经 stdin 传入，绝不作为参数：
$ embassy send --from codex-embassy@this-mac --to claude-main@this-mac --expects-reply <<'MSG'
Which auth middleware did you settle on?
MSG
# 观察回执结算（可选）：
$ embassy dashboard --live
